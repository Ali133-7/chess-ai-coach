# تطوير التحليل والتدريب والأداء

هذا تحديث متكامل للمستودع، يعتمد على مكونات المشروع القائمة. بيانات المعرفة العامة نفسها باقية، والترحيلات تضيف الجداول فقط. لا تتضمن هذه المرحلة استبدال نشر السيرفر القائم تلقائياً.

| المطلوب | التنفيذ |
|---|---|
| التحليل التزايدي | يبقى checkpoint كل وضعية في `position_scans`؛ يستأنف العامل الناقص فقط، ويستخرج النتائج النهائية من المحفوظ |
| طابور وأولوية وإلغاء | حجز SQLite ذري برمز خاص بالعامل ومدة صلاحية؛ تذاكر أولوية لوضعية يراجعها اللاعب، إلغاء يمنع الحفظ المتأخر واستئناف بلا حذف التقدم |
| ذاكرة مشتركة للوضعيات | `shared_engine_scans` مع single-flight بين العمليات، تحقق من قانونية PV، ميزانية ونسخة محرك وسياق قواعد التعادل ضمن المفتاح |
| التدريب التكيفي | أدلة مهارة محسوبة من جلسات التمارين الفعلية، اختيار جديد بحسب الضعف، ومراجعات مستحقة اختيارية دون إعادة المنجز إلى قائمة الجديد |
| معلّم يسترجع المعرفة | مطابقة محلية للافتتاحيات والوضعية ودروس المنهج، ومصادر ومراجعات محدودة للتناقضات، مع بقاء الأسهم والخطوط من المحرك فقط |
| واجهة أسرع | دمج GET المتزامنة، نسخ مستقلة للردود، إلغاء القراءة المستبدلة، حجب ردود الجلسة السابقة، تحميل لوحات البيانات عند فتحها وإيقاف polling عند الإخفاء |
| اختبارات متصفح وأداء | Playwright لعشرين حالة عبر أربعة أحجام، إضافة لاختبارات DOM والوحدات وStockfish الفعلي، وتقارير/صور وtraces في CI |

## الطابور والتقدّم

افتح «راجع مبارياتك ← تقدّم التحليل والأولوية». يمكن إعطاء الأولوية أو الإلغاء أو الاستئناف. فتح مراجعة مباراة غير مكتملة التحليل يمنحها تذكرة أولوية أيضاً. التذكرة تُستهلك عند الحجز؛ لا يحتكر مستخدم الطابور إلى أجل غير محدد. لكل حساب تذكرة بارزة واحدة، مع حدّ على أوامر API.

حجم الدفعة الأقصى أربع وضعيات. بعد عشر ثوانٍ، أو عند وصول مهمة بارزة جديدة، يسلم العامل الدور عند نهاية الوضعية التالية. البحث الجاري قد يستغرق ميزانية الوضعية نفسها، حتى 120 ثانية للمستوى العميق؛ لا نصف الإلغاء بأنه قتل فوري لعملية Stockfish. إلغاء المهمة يُبطل رمزها فوراً، لذلك لا يستطيع بحث قديم حفظ checkpoint أو إعلان اكتمال المباراة بعد إلغائها. النتائج المحسوبة كحقائق محرك عامة قد تدخل الذاكرة المشتركة، دون أن تُكتب في المباراة الملغاة.

الاستئناف يقرأ checkpoints دفعة واحدة ويمرر الرقعة تدريجياً، بدلاً من إنشاء نسخة من تاريخ اللعبة لكل وضعية في كل دفعة. ويختصر مفتاح الذاكرة تاريخ النقلات عند تصفير عداد نصف النقلات، دون تغيير هوية سياق التعادل. يحد ذلك من كلفة الذاكرة وقراءات SQLite عند استئناف مباريات طويلة.

مدة حجز المهمة 180 ثانية، تُجدد عند الحدود بين الوضعيات؛ حجز الذاكرة المشتركة هو الأكبر بين 30 ثانية وميزانية البحث +30. عند موت العامل يمكن لعامل آخر الاسترداد بعد انتهاء الحجز. رموز الحجز تمنع نتائج العامل المتأخر من الكتابة. انتظار حجز مشترك يؤخر إعادة المحاولة بدلاً من حلقة SQL مشغولة.

API مملوك للحساب ومحمي بـCSRF:

```text
GET  /api/analysis/jobs
POST /api/analysis/jobs/{game_id}/action
     {"action":"prioritize|cancel|resume|retry"}
GET  /api/analysis/metrics       # للمدير فقط
GET  /api/training/plan
```

## هوية الوضعية وحدود الذاكرة

المفتاح يشمل رقعة FEN والدور وحقوق التبييت والأخذ بالتجاوز وعداد نصف النقلات، وتاريخ حالات التكرار منذ آخر نقلة لا رجعة فيها، والوقت وMultiPV وخيارات المحرك وبصمة ملفه ونسخة خوارزمية التحليل. رقم النقلة الكاملة لا يؤثر في الحساب فيُستبعد.

هذا أكثر تحفظاً من مشاركة نتيجة كل FEN متشابه: تكرار النقلات وقاعدة الخمسين قد يغيران النتيجة. تبديل ترتيب النقلات يُشارك عندما يكون سياق القواعد المكافئ متطابقاً، ومنه الوضعيات المتطابقة بعد نقلة لا رجعة فيها. لا نشارك نتيجة عند اختلاف التاريخ المؤثر أو الميزانية. لا تشارك نتيجة بحث ضعيف بوصفها بحثاً أعمق. الكاش خاص بخط التحليل الخلفي؛ تحليلات التدريب التفاعلية ذات العقد/الميزانية المختلفة تبقى مستقلة.

كل PV مسترجع يُفحص نقلة نقلة. المدخلات غير القانونية تعاد حسابها، والطلبات المتزامنة لا تكرر البحث نفسه. الحدّ 20,000 مدخل غير نشط، وتزال الأقدم دون حذف الحجوزات الحية. البيانات المحفوظة حقائق محرك ولا تتضمن هوية اللاعب أو PGN أو البريد. لا يُعرض endpoint عام لقراءة وضعيات مستخدمين آخرين. تتأكد واجهة الطابور من المالك، حتى إذا كان الطالب الآخر مديراً.

تحليل المباراة المحفوظ قبل التحديث يُحافظ عليه كما كان؛ تغيير إعداد السرعة لا يمحو checkpoints القديمة. الكاش الجديد يطبق فصل الميزانيات على النتائج التي يحسبها التحديث. تقييمات البحث المحدود تقديرات وليست حقائق رياضية ثابتة.

## التدريب التكيفي دون Elo وهمي

تسجل جلسة التمرين المنتهية مرة واحدة: حل مستقل بلا خطأ =1، حل بعد تصحيح =0.6، كشف الحل أو التخطي =0. لكل موضوع:

```text
المؤشر = (مجموع أوزان النجاح + 2) / (المحاولات المحتسبة + 4)
الهدف = المرجع الحالي + round(300 × (مؤشر أضعف موضوع − 0.5))
```

المرجع هو التصنيف المنشور المخزن، أو هدف المستخدم إن لم يوجد؛ الهدف مجرد اختيار لتصنيف ألغاز مرجعية وليس تقديراً لتصنيف اللاعب. التمارين المولدة بلا تصنيف تبقى غير مصنفة. المؤشر استدلال مبسط مع prior معلن، وليس نسبة فوز أو مقياساً معايراً للاحترف.

المراجعة بعد 1 و3 و7 و14 و30 يوماً. الحل الصحيح قبل الاستحقاق لا يزيد المؤشر ولا يمدد الفاصل، لمنع تضخيم الإتقان بإعادة السؤال نفسه. كشف الحل أو الفشل يعيد المراجعة إلى فاصل قريب. المراجعة مقترح اختياري مستقل؛ قائمة الجديد تستمر باستبعاد ما عُرض أو أُنجز. لا نسند للمحاولات القديمة معلومات غير مسجلة: يبدأ دليل التمارين التكيفي من نتائج ما بعد التحديث، ويظل تقدم الدروس ومراجعتها القائمة محفوظاً. خطة المتابعة المولدة تستفيد من هذه الأدلة المجهولة الهوية أيضاً.

## الاسترجاع والشرح

يستخدم المعلّم وضعية محفوظة وقانونية وخطوط المحرك، ثم يسترجع ما يصل إلى ست وثائق محلية: افتتاحية بمطابقة الوضعية، أو عناوين افتتاحيات، وفقرات من الدروس بحسب تقاطع كلمات السؤال. ترتيب الكلمات حتمي وليس درجة ثقة من نموذج أو بحث embeddings. النتيجة تعرض معرف المصدر والمراجعة والترخيص، وتحتفظ بمصادر النقلات العامة.

تُحظر بعض العبارات الصريحة المناقضة للوقائع، مثل «هذه النقلة تحقق كش مات» عندما لا تحقق النقلة ماتاً. هذا فحص محدود قد يرفض صياغة ملتبسة؛ **ليس برهاناً لصحة النص كله**. تبقى `prose_formally_verified=false` ظاهرة في البيانات. الأسهم والسيناريوهات تقبل المعرفات والحركات المتحققة فقط، لا إحداثيات يؤلفها النموذج. الأسئلة العامة لا ترث رقعة أو فوائد نقلة سابقة. تعليمات الوثائق والسؤال تعامل كبيانات؛ المفاتيح وهوية اللاعب لا تدخل الاسترجاع.

## الأداء والقياسات

قياسات `Server-Timing` تشمل المعالجة داخل التطبيق، ولا تعادل زمناً شاملاً للشبكة أو وقت Stockfish. `/api/analysis/metrics` للمدير يعرض آخر 128 عينة لكل route، بحد أقصى 96 route في العملية، ومتوسطها وp95، مع عدادات الكاش والطابور من SQLite. القياسات في ذاكرة عملية الويب وتُصفّر بإعادة التشغيل؛ عدادات الكاش دائمة.

لوحة القياسات المطوية في الإدارة تعرض هذه القيم و`StudioRequests.metrics()`. عداد المتصفح يغطي GET القابلة للدمج فقط، ولا يدعي عدّ كل حركة شبكة. لا تحفظ القياسات الاستعلامات أو البريد أو نصوص المستخدم. يُعدّ Long Task عندما يدعم المتصفح تلك الواجهة، دون إرسال بيانات التصفح إلى خدمة خارجية.

نتائج الاختبارات المحددة:

- Stockfish فعلي: مباراتان اختباريتان متطابقتان، خمس وضعيات لكل منهما؛ خمس عمليات حساب وخمس إصابات كاش، بدلاً من عشر عمليات حساب.
- ثماني قراءات GET متزامنة متطابقة ضمن جلسة واحدة: طلب شبكة واحد، مع ثماني نسخ مستقلة للمستهلكين.
- 20 حالة متصفح: 320×740، و390×844، و768×1024، و1280×900؛ تشمل حدود التمرير الأفقي، اللغة، الطابور، التمرين، المودال وتبديل الحساب.

هذه ليست وعوداً بنسبة تسريع عامة؛ تعتمد الفائدة على تكرار الوضعيات والميزانية والجهاز. لا نفرض عتبة ميلي ثانية هشة على CI؛ نفرض عدد الطلبات وعدم تكرار الحساب وصحة التقدم.

اجتاز التحديث الأساسي جميع فحوص [GitHub Actions 45264350449](https://github.com/Ali133-7/chess-ai-coach/actions/runs/45264350449). وأعيد فحص العامل والمحرك الفعلي بعد تحسين المرور التدريجي: 11 اختباراً، بينها الأولوية والإلغاء والحجز والتكرار ولون صاحب الدور. التشغيل النهائي للمستودع يعيد المجموعة الكاملة تلقائياً.

## الاختبار

```bash
pip install -r requirements.lock
PYTHONPATH=.:tests python -m unittest test_analysis_runtime test_analysis_engine test_adaptive_grounding -q
npm ci
npm test
npx playwright install --with-deps chromium
npm run test:e2e
```

على Windows يمكن ضبط `CHESS_E2E_PYTHON` لمسار Python في venv و`CHESS_E2E_CHANNEL=chrome` لاستخدام Chrome المثبت. CI يستخدم Chromium المطابق لإصدار Playwright. الخادم الاختباري ينشئ قواعد مؤقتة وحسابات موسومة fixtures على المنفذ المحلي 18024، ويضبط مسارات المفاتيح إلى ملفات غير موجودة؛ لا يستخدم قواعد التشغيل أو مزود AI مدفوعاً. يرفض إعادة استخدام خادم موجود. تقارير المتصفح والـtraces والصور في artifact مستقل، ولا تُرفع إلى Git كملفات مصدر.

## الترقية الآمنة والتراجع

**يجب ترقية `studio` و`studio-worker` معاً.** العامل القديم لا يعرف حجز المهام وإلغاءها، فلا تشغل الواجهة الجديدة أمام عامل قديم. خذ نسخة SQLite متسقة ونسخة محمية للمفاتيح وفق README، واحتفظ بالصورة السابقة. جرّب النسخة على بيانات منسوخة في بيئة معزولة أولاً؛ لا تستخدم fixture المتصفح كقاعدة حقيقية.

لتثبيت أُنشئ من Compose الكامل في هذا المستودع، وبعد النسخ الاحتياطي:

```bash
docker compose stop studio-worker
docker compose build studio
docker compose run --rm --no-deps studio python -c "from studio.app import start; start()"
docker compose up -d --no-deps --no-build studio studio-worker studio-sync control-sync
```

أعد إنشاء مولد التمارين بالصورة نفسها إن كنت تستخدمه. على الخادم القائم الذي استُخدمت فيه صور overlay وsystemd، يلزم تجهيز صورة مرشحة من الكود الكامل ومراجعة Compose والمؤقتات؛ لا تعِد البناء عشوائياً من checkout قديم. لا تشغل مولّدين أو عامل مزامنة دفع مكرراً.

الجداول الجديدة: `analysis_jobs` و`shared_engine_scans` و`adaptive_attempts` و`adaptive_skills` و`adaptive_reviews`، مع فهارسها. `core.setup()` يضيفها دون حذف أو إعادة تصنيف سجلات موجودة. عند التراجع أوقف العامل الجديد قبل إعادة الصورة القديمة، واحتفظ بالجداول؛ لا تستعد قاعدة أقدم فوق بيانات أحدث دون مراجعة. حالات `cancelled` تُستأنف من واجهة النسخة الجديدة؛ لن يلتقطها عامل قديم تلقائياً.

المخططان في `database` حُدثا دون صفوف خاصة، وبقيت لقطة المعرفة العامة وبصماتها كما هي. لإعادة توليد المخطط وحده محلياً بأمان: `python -m scripts.refresh_database_schema`.

راجع [توثيق Playwright الرسمي لخادم الاختبار](https://playwright.dev/docs/test-webserver) و[تشغيله في CI](https://playwright.dev/docs/ci-intro).
